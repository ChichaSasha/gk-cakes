## K00 — ownership, identity, wire and transactions

Go API owns prices, eligibility, state and authorization; SvelteKit customer/admin
UI consumes `/api/v1` HTTPS JSON. UUID IDs, lower_snake_case, integer versions,
GBP signed 64-bit integer pence with checked arithmetic; no floats. Inputs reject
unknown fields; omitted patch fields remain unchanged, explicit null clears only
named nullable fields. UTC RFC3339 instants; local dates and recurrence use
Europe/London, never a fixed UTC offset. Reject nonexistent local times; ambiguous
DST input must specify an offset. Time rules use the persisted server receipt instant
of an authenticated, syntactically valid command; record actual commit time separately.
Duplicate command reuses its original instant. A cancellation preview is not receipt
of a cancellation request. Recheck ownership, version and state after locks.

Mutations require Idempotency-Key and existing-object expected_version. Unique
(actor or guest capability, command, resource, key) plus canonical body hash:
same request returns saved operation; changed input yields409 KEY_REUSED. Money
identities survive provider key expiry. Ordinary command keys retained30d with
business uniqueness preventing duplicate effects afterward. Ambiguous commits are
looked up before retry. Async202 returns operation_id,state,poll_after_seconds=3;
GET /operations/{id} requires identical ownership. 400 malformed;401 no identity;
403 capability denied;404 missing/not-owned;409 stale/state/key/price conflict;
422 invalid input;429 Retry-After;503 unavailable. Error body
`{error:{code,message,request_id,retryable}}` never exposes SQL/provider/private data.

Supabase manages authentication. Select browser SDK bearer sessions, private pages
rendering a shell only; API verifies ES256 signature via fixed configured JWKS,
issuer, audience=authenticated, expiry/nbf, subject and session identity. Keep
access token in memory; refresh persistence must use the provider-supported session
store qualified in GK-021 with CSP and XSS checks. No tokens in URLs/logs; private
responses no-store, clear caches on sign-out. Authorization is actor-specific:
guest order commands require an active order-bound capability and its permitted
command scope; authenticated customers require a current provider session/account
and ownership, with no staff membership requirement; staff require current provider
session/account plus active locally granted capability and object scope. Claims
require the authenticated customer branch and chef approval. Recheck revocation
and replay after locks. Provider session-check outage fails closed for authenticated
sensitive mutations; it does not impose provider login on guests. GK-021 must prove
logout/disable, guest revocation, cross-order denial and replay behavior,
not infer immediate JWT revocation from sign-out. Runtime variables/callback paths
are produced by GK-020 then explicit exact allowlists tested by GK-021; no wildcard.

Guests use an unguessable scoped order capability, digest only in DB, revocable,
private no-store; exchange link into memory then remove from URL before other requests.
Persist order_guest_capability independently of custom_request, binding digest,
order, allowed commands and revocation; rotate by revoking the old digest atomically.
Claim approval revokes outstanding guest capabilities and audits the transition.
No automatic account association by email, payer, address or Instagram. Historical
claim requires verified account + order evidence + chef confirmation. Pending claim
reveals no order details. Store safe evidence reference, approving chef and immutable
association audit; reject insufficient proof. Proposed challenge expires after30m,
single-use and bound to subject/order; generic404 on absent/expired/foreign proof.

Current production business authority is Elina as chef; Sasha has necessary technical
support access, not ordinary business override. Sandbox first manager approval is
GK-010's verified closing comment, subject22ac712e-4e38-48bb-a56d-fa7809ccc13f,
project flbgymxjelzexgoxrcss. Infrastructure Owner is not an application role.
Capabilities: chef manages policy/catalog/date exceptions/cancellations/refunds/claims;
fulfillment can prepare/ready/dispatch/handover only; technical support gets bounded
audited access and no routine money/content authority. Future roles grant nothing now.

Global lock order: command identity/unique quote conversion before resources; then
orders UUID → collections UUID → refund/goal rows UUID → config rows type/ID →
handover-day, finished-cake-lot, pickup-slot, delivery-window, discount resources
by rank then ID → reservations → ingredient/component lots ID → history/audit/intents.
Skip untouched ranks. Pure config/stock edits never acquire an order afterward.
No network under locks. Transactional domain commands enforce lifecycle, sums,

## K11 — confirmed-order recovery contract

Approved goal: no lost confirmed order/change details or essential attachment bytes;
independent daily DB+object restore points30d; nonessential upload loss≤24h; routine
recovery≤3 support hours, daily10:00–23:00 London, clock pauses overnight. These are
targets requiring GK-034/035 evidence, not current guarantees. Ordinary DB outbox
alone cannot meet zero confirmed loss if primary DB disappears before backup.

Use immutable encrypted recovery envelopes in independent B2, ordered per aggregate,
with operation ID, expected prior revision/hash, exact accepted payload/snapshots,
attachment hashes+recoverable bytes, provider/account/environment and immutable
external-operation key/body. No credentials or unnecessary PII in logs/manifests.
A per-order durable command reservation serializes revisions; other conflicting
commands wait/retry while its recovery phase is incomplete. Do not hold SQL locks
during B2/Stripe/Resend calls. Persist prepared envelope and verify independent
acknowledgment before payment dispatch/free confirmation or accepted order-change
commit. Missing B2 readiness blocks new checkout/changes with recoverable503/202.

Envelope is intent, never proof of paid/committed state. After main commit, append
outcome/version acknowledgment independently before exposing a confirmed response
or confirmation email. A DB commit followed by failed acknowledgment remains
confirmation_pending; reconciliation reuses same operation, not a second mutation.
For provider success while B2 is down, keep actual paid liability and the predispatch
envelope; show payment received/confirmation being secured, alert chef, stop further
collections. Provider success is reconstructed from authoritative account evidence,
not erased because final independent acknowledgment is missing. Free outcomes require
an independently durable outcome before confirmation is visible. Essential blobs
must be copied before their accepted reference is committed.

Before every money/email dispatch, independently retain its immutable dispatch intent
and identity, then mark local started; missing return acknowledgment is unknown.
Independent completion evidence records outcomes without pretending cross-provider
atomicity. Restore freezes outgoing payment/refund/email jobs; choose validated DB
snapshot, restore object bytes, replay ordered prepared/outcome envelopes with unique
operation IDs and prior-version checks, apply deletion/hold rules, then reconcile all
provider operations in loss window including those without local IDs. Ambiguous
prepared operations cannot be blindly executed; unresolved facts go to chef queue.
No reopening until order/attachment manifests, balances, pending reservations and
send identities reconcile. Restore must demonstrate no duplicate charge/refund/email.

Delivery ownership: GK-020 establishes schema/config access. GK-024 implements
the minimal K11 coordinator, independent B2 prepared/outcome records, essential
blob copying and dispatch journal before its first email dispatch. This explicitly
extends its ownership to shared recovery code/schema and B2 integration, coordinating
shared migration files; it is not email-files-only. GK-025/026/027 already depend on
GK-024 and cannot expose confirmation or dispatch until this prerequisite passes.
GK-034 consumes this protocol for scheduled backups, operational alerting and restore
tooling; it may work on disjoint release workflow files early, but its recovery
integration requires GK-024. GK-035 proves the complete system.

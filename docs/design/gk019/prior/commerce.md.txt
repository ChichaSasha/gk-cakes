### Concrete financial and capacity mutation gateway

Shared K04 r3 accepts **typed PostgreSQL command functions**, called from the modular
backend, as the enforced boundary for cross-row financial/resource invariants. This closes
the financial pilot's “choose an enforced gateway” blocker at design level:

- A non-login, non-superuser owner owns protected tables and `SECURITY DEFINER`
  functions. Runtime API/worker roles are neither owner nor members able to SET ROLE
  to owner/migrator, have no BYPASSRLS/DDL, and cannot directly INSERT/UPDATE/DELETE/
  TRUNCATE protected order lifecycle/snapshot, capture/refund/goal/observation,
  reservations/resource counters or discount usage. No generic SQL/patch function.
- Grant runtime only named function EXECUTE and required reads; internal helpers
  are not callable by runtime. Revoke default PUBLIC EXECUTE, set default privileges,
  and create grants/functions in one migration transaction. Qualify objects; fixed
  trusted search_path with pg_temp last, no runtime schema CREATE. Database provider
  admin/service roles are excluded from runtime. Separate worker grants for verified
  observation application and dispatch admission; customer requests cannot call them.
- Functions take explicit command data, acquire prescribed locks, validate state,
  amount/currency/allocation/version and resource limits, and append audit/outbox.
  Backend authenticates principal and capabilities; functions additionally validate
  the passed local actor/ownership where applicable. This gateway prevents accidental
  DML bypass by runtime; it does not make a compromised trusted backend truthful.
- `create_checkout`, `apply_collection_evidence`, `expire_unpaid_order`,
  `cancel_order`, `reserve_refund`, `apply_refund_evidence`, `admit_refund_dispatch`,
  `move_pickup`, `transition_order` and `set_resource_capacity` are concrete command
  boundaries, not a promised function count. Keep each atomic outcome in one call;
  split reusable SQL internals only when actually shared.
- Migrator can change the schema by necessity; its credential exists only in the
  controlled release/maintenance path. Data corrections call the same routines;
  exceptional migration/backfill pauses dispatch, follows locks/invariants and runs
  real-DB invariant checks before resuming. No claim that SQL can prevent its owner
  or a superuser deliberately bypassing controls.

[PostgreSQL function security](https://www.postgresql.org/docs/current/sql-createfunction.html)
and [privileges](https://www.postgresql.org/docs/current/ddl-priv.html), checked
2026-09-21, underpin this design. Real-role DML/EXECUTE/SET ROLE denial tests and
empty/upgrade/restore permission verification remain mandatory; no such test ran.

### Global transaction discipline

Normal writer order: existing `order` rows by UUID -> collection/capture rows by
UUID -> refund rows by UUID -> mutable commercial configuration rows (catalog/
policy) by type+ID -> resource rows in this fixed rank and ID order:
production_day, finished_cake_lot, pickup_slot, delivery_window, discount -> their
reservation/application rows -> inventory ingredient/lot rows by stable ID -> append
command/history/audit/notification results.
Skip untouched ranks. Queries must explicitly order lock acquisition; never rely on
an unordered IN query. No provider/network call inside any transaction holding locks.

Creation first claims the unique actor+create-command+key identity, then inserts its
private new order and unique quote-conversion relationship, before shared resource
locks. Same-key/quote losers wait/retrieve original committed identity or roll back;
they must not hold resources while waiting for that unique creation claim. Existing
order commands resolve idempotent replay under the order lock; replay reauthorises
and reads stored result without acquiring another order. Worker job claim releases
its short queue-row lock before any order-first transaction. Bulk commands collect
and lock all affected orders by UUID before resources; no resource-first backfill.

At READ COMMITTED, a command locks current configuration rows while comparing quote
versions, then capacity/discount rows before admission. Admin catalog/config writers
use the same configuration locks and never then acquire order locks. Immutable
versions make committed snapshot reads stable. Resource-only capacity/blackout edits
lock resource rows, check held+committed and finish without touching orders. Reject
capacity reduction below that sum; closing new sales (`accept_new=false`) can preserve
old commitments. A mere pre-query of affected orders does not prevent concurrent new
bookings: if a future edit actually changes orders it needs a reviewed coordinated
closure/order-lock protocol, not enumeration presented as a phantom-proof lock.

Local arithmetic CHECK constraints defend counters; functions make counters and
reservation rows change atomically and reconcile their sums. Refund cross-row sum
is computed under order/capture lock, not a false row CHECK. Deadlock/serialization
errors get at most three whole-transaction retries within the shared deadline;
client still uses the original key. [PostgreSQL row locks](https://www.postgresql.org/docs/current/explicit-locking.html),
checked 2026-09-21. No process mutex or scheduler punctuality establishes correctness.

## Money, scheduling and race rules

### Quote, discount and commitment

Use checked integer pence arithmetic, bounded quantities and immutable line IDs.
Website collection is 100% of accepted total, one active collection per order.
Recommend one code, no stacking, percent eligible goods only, free delivery only
on eligible chef delivery; all four are Creator policies awaiting approval.
Proposed bps percent rounds aggregate eligible discount half-up, then allocates by
largest remainder with stable line-ID ties. Example 1001p+1000p at 10% gives 200p
allocated 100p/100p, net 1801p. Eligibility, validity [start,end), usage cap and current
rule version are rechecked under locks at commitment. Success consumes held usage;
terminal unpaid expiry releases it; unknown retains it. Admin changing code cap
cannot go below held+consumed; new expiry/rule does not rewrite an accepted order.
A rejected checkout leaves no usage or partial capacity allocation.

Owner reports no separately added VAT; cake-after-discount/delivery allocation is
supplied. Legal verification, rounding and ready-cake scope remain unresolved. A 100% discount can produce zero total: a website order must not be sent
to a provider pretending positive funds were captured. Before S01 is Ready Creator

### Checkout, expiry and late payment

1. Quote is advisory, no scarce resource hold. Commitment claims command/quote once,
   locks/revalidates sources, then reserves all line production units OR ready stock,
   handover/pickup OR chef-delivery window and discount in one DB transaction. Mixed
   basket is permitted only if every line is feasible for the same promised
   fulfillment; otherwise return 422 with unchanged resources. Create immutable
   awaiting_payment order, collection intent, audit and applicable notice together.
2. Before session-create dispatch, take order-first locks, check not closed, policy/
   promise still feasible and no quarantine, persist immutable provider key/body and
   dispatch_started_at. Release locks, call provider, persist reference/evidence under
   locks. API returns pending operation within proposed 3s, not synchronous uncertainty
   as failure. No new operation merely because response/worker lease was lost.
3. Proposed card-only 30-minute Stripe session must be qualified in sandbox. Stripe
   documents expiry 30 minutes–24 hours **after provider session creation**, so do not
   set a guessed `order.created_at+30m` provider deadline after an async delay. Persist
   selected allowed duration and actual returned expiry. Before dispatch verify the
   minimum window fits lead-time/production cutoff; otherwise close safely or request
   another date. Hold deadline tracks reconciliation; UI shows provider expiry only
   after known. Quote expiry and payment-session expiry are distinct.
4. Never-dispatched collection can be closed/released under the same lock only if
   dispatch_started_at is null and no provider request was admitted; set cancelled
   so a queued worker cannot subsequently send. Once dispatch admitted, “no provider
   ID yet” is unknown, not evidence no request ran. At due time retrieve/expire the
   same provider session as applicable, verify terminal unpaid **and no successful
   or unresolved underlying payment**, then release all holds/discount once and set
   expired. HTTP failure/processing retains holds and queues reconciliation/manager
   alert. Approved exceptional forced release records reason and future money liability.
5. Signed inbox is durable before 2xx; validate account/environment/object/amount/
   currency against immutable operation, retrieve current payment evidence outside
   locks, then apply once under order-first locks. Valid capture commits holds and
   discount and confirms only if the still-pending order's promise remains feasible.
   Stale reconciliation generation cannot overwrite a newer authoritative result;
   reschedule a fetch. Session completion/return URL alone is not capture proof.
6. Success after hold release or after lead-time/cutoff failure records all money
   but does not reopen expired/cancelled lifecycle or trigger fulfillment. Shared K04
   r3 selects durable full-return goal, refund execution/reconciliation and manager
   recovery without fulfillment as the default. GK-025 owns this minimum refund
   core before collection exposure; GK-026 extends it. Reacquisition or a replacement
   order remains blocked until explicit feasibility/consent policy is accepted;
   never infer revival from payment success or bypass quote/order uniqueness.
7. Extra capture, mismatched amount/currency, external refund or dispute freezes new
   dispatch/fulfillment pending reconciliation. Store every verified external fact,
   not only those fitting a local cap. Pilot quarantine preserves local unknown
   allocations and external observations separately, with possible exposure visible.
   Dashboard action before freeze may already be in flight; local freeze does not
   pretend to revoke a provider request. No second collection or return without proof.

### Production, cancellation, pickup and manual entry

Owner BO-GK-001.production_start requires 48 hours after placement with earlier
manual confirmation starting work; ready preparation is separate and records actual
start. Placement-event and state-action semantics need GK-019 review. The old
pickup-minus-X proposal is superseded as a design assumption. Under the existing
technical discipline sample clock_timestamp() after order lock, retain effective
versus recorded time and materialize due events idempotently despite late workers.

BO-GK-003 permits <=4-day customer cancellation with no cake refund; cancellation
and money entitlement are distinct. >4-day/not-started 50% cake and unperformed
delivery, started/ready money treatment, and conflicting ready-cake 3-day rule are
in the owner data contract. Do not implement the former blanket pre-production-only
cancel gate. Pickup moves change the refund date/time, not automatically the start
clock; reopening and complete state matrix remain unresolved.
Pickup move locks order, any affected financial/config rows then both resource IDs
in canonical order. At equality/due time materialise start; apply separately approved
pickup deadline/state rules. Target capacity/eligibility, promised production date,
old/new policy and slot timezone are checked. Increment target and release old in
one transaction, update appointment/history/notice/version once. Same target is an
idempotent no-op. Invalid/full target leaves old appointment; if timed start must be
materialised, commit that valid transition while returning the move rejection with
the unchanged appointment. A move is never a delivery-mode/production-date edit.

No implicit swap across two customer orders: if both destinations are full, each
move fails retaining its slot; a future explicit manager swap is outside scope.
Admin changing policy/slots affects new commitments only under recommended snapshot
rule. Existing-slot deletion/interval mutation is blocked; close future sales and
create replacement slots. Customer consent/recovery required for changing booked
promises. Timezone labels include offset for repeated London times; nonexistent
spring-forward wall times reject, ambiguous autumn times require offset selection.

Manual order creation uses the same quote/order and all resource admission. Default
payment is a 100% hosted link; no provider collection is invented from conversation.
For owner-permitted Revolut invoice payment, capture provenance is
`offline` with unique evidence reference, amount/currency, verified manager and
observed time; simultaneous online/unknown payment blocks recording until resolved.
It follows the same capacity transaction and immutable agreed total. Offline return
uses durable obligation + manager evidence of actual return, never provider POST.
Revolut invoice is owner-accepted for selected orders; verification authority,
cancellation conflicts and race semantics remain GK-003/019 blockers. Capacity
can never be bypassed by an admin “paid” switch. Quote amendments race checkout under
source/version locks and force explicit reconfirmation when checkout has not committed.

Production reservation remains a commitment after work starts; cancellation releases
only usable future commitments by approved policy. Consumed ingredients, occupied
production effort and removed finished stock are not automatically replenished.
Cancellation before production can release planned ingredient demand once; physical
adjustment belongs to inventory. Finished-stock reservation release restores saleable
availability only if that stock still physically exists, is usable and has not been
consumed/handed over; otherwise retain removal and raise exception. Same transaction
or durable inventory transition identity prevents duplicate consumption effects.

Fulfillment transitions require paid/approved financial clearance and valid state:
ready follows production/preparation, dispatch requires chef-delivery mode and ready,
complete records actual handover/delivery evidence. Customer-arranged courier uses
booked pickup/handover. Delivery exception retains capacity/history and actionable
contact task until reviewed; it does not automatically complete, refund or restore
stock. Optional delivery_reference is enough for a later adapter; no interface or
provider orchestration is justified now.

## Outcome and smallest complete option

Recommend one customer journey rather than separate storefront experiences:

1. A public gallery distinguishes inspiration from an orderable cake and shows
   authentic imagery, a starting GBP price, servings and availability language.
2. A cake detail page makes the next decision explicit: **Choose this cake** for
   current variants or **Request changes** for a recoverable custom summary.
3. A public schedule shares only advisory day-level availability. It never shows
   customer, order or capacity-count data and never reserves a date.
4. The custom flow saves a versioned draft and summary, then offers **Copy
   summary** and **Open @gk.cake.london** as separate user-controlled actions. Neither
   action claims that Instagram received a message.
5. An optional account contains the customer's own order history/timeline,
   favourites and private Instagram handle. Signed-out favourites stay on that
   device and merge only after the customer chooses.
6. Reorder always rebuilds current choices, price, allergen revision and
   availability. It never clones the historical order or proceeds directly to
   payment.

This covers the requested customer tasks with the existing modular monolith,
K00–K02 APIs and one shared UI. Skip a search service, recommendation engine,
social-login linkage, Instagram messaging integration and separate favourites
service. Add them only after observed demand and an approved contract.

Adjacent requirements C05/C06/C10/C14–C17 and A07 remain owned by checkout,
financial, scheduling, notification and manual-order packets. This packet shows
their entry points and dependencies but does not redefine their rules.

## Rules and state transitions

### Catalog, availability and allergens

- Inspiration, product and variant are different. An inspiration may support only
  **Request changes**; an active product with an eligible variant may support
  **Choose this cake**. The UI never infers orderability from having a photo.
- Price, servings, recipe/allergen revision and availability come from the API.
  The UI may preserve a viewed value while refreshing, but must label it stale and
  require review when the server changes it.
- Ingredient/allergen and chef-approved cross-contact wording appear before the
  purchase path. Missing approved wording disables buying that variant; it does
  not show “allergen free” or guess from recipe rows.
- Public schedule stays advisory and private; owner now requests standard available
  slots. Numeric remaining-versus-total display needs clarification; the former
  flags-only assumption is not settled owner policy.
- Hybrid ready stock needs a distinct badge and availability source. Do not imply
  a made-to-order date rule covers ready stock until the scheduling packet settles it.

### Custom request and Instagram handoff

Proposed draft states are `draft -> ready_for_handoff -> archived`; quote/order
conversion belongs to Orders and does not make the request itself “paid”. Each
accepted edit uses `expected_version`. At summary generation, store one immutable
revision and display its short request reference. That revision pins the exact
ready catalog image bytes by immutable object key/version and records the catalog
image revision plus display metadata; a later catalog upload or archive changes
the public cake, not what this request means. Replacements always use a new immutable
key. Pin creation and cleanup admission lock/serialize on the same image-reference
row: a committed pin blocks cleanup, while a cleanup tombstone that wins first
causes 409 `REFERENCE_UNAVAILABLE` and asks the customer to choose a current image.

The summary includes only the approved request fields, date as London local date,
servings, the frozen inspiration image/reference and requested differences. The
text handoff contains a safe request reference rather than a secret object URL.
Authorized request owner/capability retrieval may display the frozen image; a
manager retrieves it only through the chef request association. The agreed quote
records the request summary revision and frozen image provenance. It excludes
security capability, contact data not intended for the chef and any assertion of
availability or price. Buttons behave as follows:

- **Save draft**: persists under the current owner/capability and confirms where
  it is saved. Signed-out browser-only save says “Saved on this device”.
- **Copy summary**: uses the browser clipboard when allowed; failure keeps a
  selectable text block and says “Select and copy this summary”.
- **Open @gk.cake.london**: opens the approved account/profile/conversation target after
  setup validation. It does not pre-announce success.
If clipboard or Instagram is unavailable, the exact summary and request reference
remain on screen and in the saved draft. No timer, reload or failed open discards it.

### Identity, profile, history and claims

Managed authentication and local authorization remain the K00/ADR-0005 candidate.
No provider is accepted. The UI may define sign-in/out/session-expiry behavior, but
token storage, browser session architecture, claim proof, guest capability and
account-link decisions are high risk and **must remain provisional until a fresh
Astra integration assessment accepts them**.

Hard constraints already shared and not reopened here:

- every private read checks the current verified subject and object ownership;
  unknown and foreign order IDs have the same 404 behavior;
- Instagram handle, typed email, delivery address and order number alone never
  prove ownership or link an order;
- a historical claim needs verified contact plus an order capability/challenge,
  is expiring, single-use and audited, and cannot reveal whether another account
  owns an order;
- staff roles come from active local membership, never token metadata alone;
- sign-out clears private in-memory/browser caches and private pages use no shared
  cache. A service worker must not cache authenticated API responses.

Profile editing trims only approved surrounding whitespace, bounds input, escapes
output and permits explicit clearing with JSON `null` under K00. Store a display
handle rather than promising Instagram ownership. Exact syntax (`@`, Unicode,
length and case rules) needs the approved account/device setup evidence.

Order history shows human labels derived from separate order, payment/refund and
fulfilment states. It never collapses “cancelled” into “refunded” or a provider
pending state into failure. New unknown enums show “Status updating — refresh or
contact the chef” and enable no destructive action.

### Favourites and reorder

- Signed-out favourites are a local set of stable cake IDs. The UI says “Saved on
  this device”; clearing browser data can remove them. Privacy classification for
  this storage remains a Creator review item.
- After sign-in, show local/account counts and ask **Add these favourites to my
  account** or **Keep account favourites only**. Never silently upload or erase.
- Merge is set union through existing PUT operations. A retry reuses the original
  idempotency key per item, preserves local IDs until acknowledgement and
  reauthorizes the current actor before returning replayed results. First release
  has no batch or generic sync endpoint.
- Archived favourites remain in the account with “No longer available” and a
  **Request something similar** action when K01/K02 can resolve a safe inspiration.
- **Reorder** starts K02 `POST /reorders` with an owned source order. The response
  must show current size/servings, GBP price, allergen revision and date options.
  Any change is explicit; unavailable/archived source offers a custom request.
  Checkout/payment starts only after a new current quote is reviewed.

```mermaid
sequenceDiagram
  participant C as Customer
  participant UI as Account UI
  participant API as Orders/Reorder
  participant DB as PostgreSQL
```

### Reconciled r4 decisions and remaining gates

The first draft's catalog representation, archived-source recovery, custom draft/
summary routes, favourite merge, profile version, order projection and reorder
changed-fact questions are historical: K02A resolves them. The catalog payload is
`kind`, `archive_state`, `orderability`, images, variants, nullable starting GBP
price, recipe display revision, allergen approval and stock mode. Public archived
detail is 404; authorized snapshots alone can request similar. First release uses
per-item favourite set union and no batch/sync engine or persisted sent self-report.

Remaining active gates are business/provider decisions rather than wire ambiguity:
exact mandatory custom fields and signed-out capability remain GK-003; managed
identity/session and historical-claim challenge delivery/expiry/revocation remain
GK-004/GK-019 plus chosen-provider and Creator decisions. K02A's `/order-claims`
proposal is not implementation-ready until that Astra-qualified prerequisite is
embedded in GK-021. Sign-out clearing the UI cache does not revoke an issued token.

Shared r4 now requires for C12 that the summary revision contain the
frozen inspiration ID, exact catalog image revision, immutable object reference/
version and safe image metadata. Object writes use new immutable keys. Storage
cleanup treats that reference as a pin, and pin creation/cleanup admission serialize
on the same image-reference row. A cleanup tombstone prevents a new pin and summary
freeze returns 409 `REFERENCE_UNAVAILABLE` rather than a broken reference.
Owner/capability reads and the manager's associated request view may retrieve it;
other actors receive 404. The image endpoint returns a short-lived authorized URL
and safe revision metadata after each authorization check; expiry refreshes through
that endpoint, never a permanent public key. Quote creation records the exact
summary/image provenance. Catalog replacement/archive cannot release the pin. Only
the GK-005/Creator-approved explicit request/quote-deletion path may release it
atomically after every retained link permits; retention duration remains policy,
not invented here.

Proposed error vocabulary for reconciliation, within K00's envelope:

| Status/code | UI meaning | Retry/recovery |
| --- | --- | --- |
| 401 `AUTHENTICATION_REQUIRED` / `SESSION_EXPIRED` | Sign in to view private data | Reauthenticate, then return to the safe task; never replay a mutation without its original key |
| 404 `NOT_FOUND` | Resource unavailable or not owned | Same copy for unknown/foreign; offer gallery/account navigation without revealing existence |
| 409 `STALE_VERSION` | Draft/profile changed | Fetch current, preserve local edits separately and ask before replacing |
| 409 `PRICE_CHANGED` / `RECIPE_CHANGED` | Current reorder/detail facts changed | Show old viewed fact only as context, show current fact, require explicit review |
| 409 `CAKE_UNAVAILABLE` / `CAPACITY_UNAVAILABLE` | Variant/date cannot continue | Pick another current option or start custom request; no automatic substitution |
| 409 `KEY_REUSED` | Retry key was used with different input | Stop; create a new key only for a deliberately new action |
| 422 `INVALID_REQUEST` / field code | Customer input needs correction | Link plain-language errors to fields; retain safe input |
| 429 / 503 | Temporarily unavailable | Respect `Retry-After`; read retry within K00 budget, mutation same-key replay/operation lookup |
| 404 `CLAIM_UNAVAILABLE` | Claim cannot be completed | Same copy for missing/expired/used/foreign; challenge delivery/expiry/retry awaits the GK-019 provider/policy gate |

Compatibility follows K09: add optional response fields, tolerate unknown fields and
show safe unknown enum states. A UI requiring a new field activates only after API
capability is present. No customer release may assume simultaneous API deployment.

## Master r5 selected-image boundary correction

The focused independent r4 reviewer found that post-freeze retention was sound
but the selected revision did not cross the API boundary. The master applied the
qualified reviewer’s explicit boundary recommendation below; earlier r4 hashes
remain author-input history. This is a shared contract integration correction,
not evidence of model unsuitability; Sol pilot qualification remains pending
independent re-review of this exact successor.

Selected-image wire contract (C12): each ready public catalog image returns
`{image_revision_id:UUID,url,alt,width,height}`. The UI retains the exact revision
ID it displayed/selected; it does not infer the source from the latest gallery URL.
`POST /custom-requests` carries `{inspiration_id:UUID,image_revision_id:UUID,...}`
for an inspiration-based request. Generic requests omit both or send both null;
the server stores both null. Supplying only one returns422 INVALID_REFERENCE_PAIR.
The draft and GET response retain both IDs. PATCH changes or clears the pair
atomically with expected_version; omitted pair means unchanged. Never accept a
client object key or arbitrary image URL as proof of the selected catalog image.

`POST /custom-requests/{id}/summary` requires key plus
`{expected_version:7,image_revision_id:UUID|null}` matching the stored draft. A
mismatch returns409 STALE_VERSION and requires refreshing the selected source;
no-inspiration drafts require null and freeze a summary with no image/reference pin.
Resolve object key/version server-side by the supplied image revision, verify it
belongs to the supplied inspiration and is a published ready image accessible via
that active public inspiration (or an already-authorized retained request revision).
Replacement does not silently switch A to B: a superseded published A may be pinned
while its inspiration remains active and bytes remain retainable. Wrong association,
non-visible/private, archived-before-initial-freeze, missing or cleanup-tombstoned
selection returns409 REFERENCE_UNAVAILABLE without an existence detail or substitute.
Retained summary retrieval after catalog archival follows the owner/manager rule.

Regression: customer displays/selects A, then catalog replaces A with B before
creating the draft or freezing its summary. The explicit A ID yields the exact A
pin/bytes if still permitted, otherwise REFERENCE_UNAVAILABLE and an explicit
reselection path. Never return/pin B without a new customer selection. Generic
no-inspiration request freezes without an image; half-pairs and foreign-image
associations fail without a request image pin.

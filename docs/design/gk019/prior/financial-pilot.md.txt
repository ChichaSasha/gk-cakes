## Outcome, boundaries and choices

The customer can cancel an eligible order and see the refund's actual progress.
The chef can cancel and return the full payment, or issue a partial refund, without
competing requests returning more than was captured. Starting production competes
with cancellation on one database row. Order cancellation is distinct from refund
completion; provider uncertainty remains a reserved obligation with a recovery owner.

| Decision | Small option and alternative | Recommendation / acceptance owner |
| --- | --- | --- |
| Production boundary | Creator selected manual start OR admin-configured X hours before pickup; alternatives for pickup edits are frozen cutoff or recomputation | Recommend earliest manual/timed trigger, frozen cutoff that pickup changes never extend. X and rescheduling behavior await Creator answer; positive eligibility additionally requires server time strictly before cutoff. Hybrid ready-stock interpretation also needs an explicit policy. |
| Customer refund | Full remaining captured payment on eligible cancellation; alternatively policy-based deductions | Full remaining payment is simplest candidate, but C06 alone does not approve deductions or allocation. Creator decides UK policy and wording; no legal interpretation is approved here. |
| Admin cancellation | Full return in confirmed/in_production/ready, with reason; alternatively narrower exception matrix | A01 requires full-return capability. Creator decides the state matrix, including completed orders; no customer entitlement inferred from an admin exception. |
| Partial allocation | Chef chooses component amounts bounded by purchased refundable components; alternatively server prorates agreed components | Explicit allocation avoids hidden rounding but adds chef input. Creator must decide tax/delivery/discount allocation; server derives component ceilings from snapshots. Implementation blocked. |
| Transaction design | One PostgreSQL transaction and parent order lock; alternative serializable transactions | Parent lock plus restricted mutation path is sufficient for a single order; simpler operationally. Real PostgreSQL interleaving checks still mandatory. |
| Provider | One selected payment provider; alternative manual provider-dashboard operation | Evaluate Stripe as a candidate, not selected. Dashboard-only operation cannot by itself give this website's coordinated pending state. No multi-provider framework. |

Proposed scope is one capture per order in confirmed launch currency GBP, collected at 100% under
C05. Master must accept that limitation and define duplicate/late capture handling
in checkout before implementation readiness. Financial rows still identify each
capture; an unexpected second capture freezes automatic refunds and opens a
discrepancy for reconciliation, rather than dropping money from the record.
Manual/offline payments need explicit provenance and a separate human-confirmed
return path; never send a provider refund for an offline payment. Neither path is
silently declared covered by this pilot.

This packet does not design checkout/expiry, stock consumption, scheduling or email
transport. Their integration requirements below remain mandatory master-owned work.
No refund restores perishable stock. Performance proposal: short per-order local
transactions and indexed recovery scans; no numeric SLA accepted. Bootstrap measures
lock wait and API latency under an agreed small-shop workload, then proposes budgets.

## Proposed data and constraints

Use existing modules from shared-r1 in one backend/database. All IDs UUID except
opaque provider IDs. Instants UTC RFC3339, stored as timestamptz; policy snapshots
hold IANA shop timezone only when a local-time rule is approved. Money is signed
64-bit integer minor units with a validated ISO currency; accepted inputs must be
positive and within persisted captured/component totals, using overflow-safe sums.
Examples use fictional amounts in confirmed launch currency `GBP`; display shop time as Europe/London. Timed cutoff is an absolute UTC instant derived from an unambiguous pickup instant minus approved elapsed X hours, not a subtraction on ambiguous local clock text.

`reserved_total` is the sum of operations in reserved/submitting/pending/unknown/
requires_action; `returned_total` is the sum currently confirmed succeeded.
For the **controlled allocation ledger** of each capture:
`0 <= reserved_total + returned_total <= captured_minor`. Unmatched/conflicting
external provider facts live in provider_observation until reconciled and are not
forced into this capped ledger. Any unresolved financial observation/discrepancy
sets capture reconciliation_state=quarantined and spendable `available=0`, regardless
of the ledger subtraction. Display controlled reservations/returns separately from
observed external amounts and worst-case unresolved exposure; never claim the
ledger cap proves the provider has not over-refunded.
Never free an unknown amount because a timeout, worker lease or idempotency key
expired. No mutable balance counter is necessary: lock the order, then calculate
from its few indexed capture/refund rows. Cross-row sums cannot be a ordinary row
CHECK: restrict business table writes to reviewed database routines (or a single
equivalently enforced mutation gateway) that take the lock and validate the sum.
Before Ready choose the concrete enforcement; migrations/admin maintenance must
obey it too. Direct uncontrolled SQL writes invalidate this guarantee.

Partial allocations and succeeded/reserved component sums cannot exceed the
approved refundable purchased component values. Keep discount application and
tax/delivery breakdown from immutable checkout snapshots; do not prorate original
undiscounted prices or independently round each refund without the accepted rule.
Full-return target includes all payment already returned/reserved, not an extra
full charge. A refund goal is not itself an additional reservation.

Retain command identity, operation and safe provider evidence while obligations
remain unresolved; never delete unresolved records on a timer. Exact financial,
audit and personal-data retention/pseudonymisation requires approved UK retention
policy and business/legal details. Names/addresses belong to existing order/contact records, not this ledger.
Backup/restore tests must show unresolved intents and inbox identities survive;
after restore freeze dispatch until provider reconciliation establishes no lost
external successes. Do not replay the restored queue blindly.

## Atomic operations and lock order

Canonical lock order for every related writer: order rows in UUID order -> capture
rows in UUID order -> refund rows in UUID order -> scheduling capacity/hold rows in
master-agreed key order -> append audit/notification/command rows. Normal request
touches one order. Worker claim uses a short separate transaction and releases its
row lock before entering this order-first path. Scheduling must never acquire an
order lock after capacity; master must reconcile checkout/reschedule with this rule.
No network calls while holding these locks. PostgreSQL row locks serialize competing
writers until transaction end; consistent acquisition order reduces deadlocks.
[PostgreSQL locking documentation](https://www.postgresql.org/docs/current/explicit-locking.html), checked 2026-09-21.

1. **Customer cancel:** authenticate, locate owned order, begin and lock order;
   resolve existing command (same fingerprint returns original reference; changed
   fingerprint conflicts). Check current state positively against approved policy,
   expected version and snapshot. After the order lock, sample server wall clock
   (`clock_timestamp()`, not transaction-start time). If the frozen cutoff is due,
   atomically materialise the permitted timed-start transition/audit/intents, commit
   that transition and return cancellation-ineligible without any refund intent.
   Delayed scheduler delivery never extends eligibility. For proposed policy only
   `confirmed` with no manual start and current time < cutoff is eligible.
   Lock captures/refunds, reject/freeze discrepancy as appropriate, set cancelled,
   create goal and reserve remaining amount `target - returned - active_reserved`
   (zero means no new provider operation), release appropriate production/pickup
   commitments through scheduling in this transaction, write audit, cancellation
   notification and command, increment version, commit. Failure rolls all back.
2. **Start production:** manual API and due-job caller use the same order lock and
   transition routine; only confirmed -> in_production. Manual call checks staff
   capability/version; job authenticates internally and uses persisted cutoff, not
   a user-supplied time. Before cutoff the job is a no-op; at/after cutoff it applies
   one timed transition. Unique business transition identity `(order_id, production
   start)` makes repeated jobs/manual commands no-ops or original-result replays
   once applied; never duplicate inventory/notification effects. Store source and
   effective start (manual action time or frozen cutoff) separately from recorded-at.
   If a manual action arrives after the timed cutoff, record timed effective start;
   whichever caller materialises it cannot rewrite when eligibility ended.
   Set history/notification atomically.
   If cancel committed first, manual request returns 409 and due job no-ops with no
   production mutation. If start committed first, customer cancel returns 409 and
   creates no goal/refund. A caller waiting before cutoff but acquiring the lock
   exactly at cutoff loses cancellation eligibility.
3. **Admin partial refund:** same lock order; amount/allocations/auth/reason checked;
   `amount <= captured - returned - active_reserved`; reserve once, audit, durable
   notification intent and command commit together. Lifecycle stays unchanged.
4. **Admin cancel + full return:** use approved separate state matrix and the same
   transaction as (1). Target is full captured payment; prior confirmed/pending
   partial refunds count towards it. No additional refund when all funds reserved.
   A cancelled order may still have an open goal; reloading it is recovery, not a
   second cancellation. Other partial commands cannot consume beyond the goal/limit.
5. **Resolve outcome:** retrieve evidence outside locks; under order-first locks
   verify expected lease/reconciliation generation and unchanged capture identity,
   apply new authoritative status, recompute goal satisfaction and emit each status
   notification once. Failed/cancelled operations release reservation only with
   definitive provider evidence. If the goal becomes underfunded, mark needs_attention
   and show exact shortfall; an authorised retry reserves that shortfall under lock.
   Do not silently consider the full return finished after a failed partial attempt.

**Pickup move integration (proposal awaiting approval):** lock the order before
old/new slots, sample server time and enforce the effective production cutoff. At
or after it, materialise timed start before applying the approved pickup-move
policy; a move never restores cancellation eligibility. Under the recommended
frozen rule, moving earlier/later leaves production_cutoff_at unchanged; whether
that makes an earlier pickup infeasible is revalidated by scheduling and can reject
the move without changing the original slot. If Creator selects recomputation,
the replacement policy must explicitly arbitrate earlier/later cutoff changes and
rewrite these race tests before readiness. Admin X changes affect new commitments
only under the proposed snapshot rule; existing orders never silently reopen.
A missing X/cutoff blocks policy-dependent confirmation/start/cancel rather than
substituting an invented number. Ready-stock cake production predates its sale;
Creator must define the order-level preparation/cancellation boundary for that
branch before applying made-to-order timed-start rules to it.

If an external refund not in the app is discovered, record its verified identity,
amount, status and evidence revision in **provider_observation**, outside the capped
allocation ledger, under the same order lock; atomically quarantine the capture.
Do not first attempt an import that must violate the controlled ledger sum. Set
available=0; block new reservations, recovery payouts and new provider-create
dispatch. Record every distinct provider fact, even an observed actual total above
capture. The chef sees local confirmed/unknown amounts, observed external returns,
possible total exposure and the discrepancy, not a falsely balanced account.

Quarantine retains all unknown reservations; it does not revoke an already sent
request. A worker checks quarantine under the order lock immediately before marking
an operation dispatching, then releases locks before the call. A request already
in flight (or crossing that external boundary concurrently) can still complete;
its result remains evidence to reconcile, not proof that the freeze was instantaneous
at the provider. No further create is admitted after the quarantine gate. Provider
limits are a required capability, but the local schema must represent their failure.

Reconcile complete provider records and identities outside locks, then atomically
apply supported dispositions under the order-first gateway: (a) bind an observation
to its existing operation and reclassify its reservation; (b) release/reclassify a
local reservation only with definitive nonexecution/failure evidence; (c) import a
distinct external return into the controlled ledger only when the cap remains valid.
An unmatched observation does not by itself prove which local request failed. If
safe reconciliation is impossible or actual external returns exceed capture,
retain quarantine, evidence and economic exposure as an explicit discrepancy for
manager/provider resolution; never reduce an observed amount or erase an unknown
operation to make the invariant pass. Unfreeze only after every material observation
is matched/disposed with evidence, unresolved external requests are accounted for,
and the allocation invariant and provider balance agree. Keep the observation/audit
history after import. Disputes/chargebacks use the same freeze and evidence path
pending provider-specific resolution to avoid double reimbursement.

## API, idempotency and provider recovery

Proposed JSON API `/api/v1`, following shared K00. Nonnull required fields; optional fields omitted, not empty or
null. No currency conversion. Safe GET responses may include nullable timestamps
and provider references only for authorised staff. Version mismatch gives 409;
client refreshes and reconfirms changed amounts, never silently changes a request.

| Producer -> consumer | Request | Response and failure |
| --- | --- | --- |
| Customer UI -> Orders `POST /api/v1/orders/{id}/cancel` | `Idempotency-Key: UUID`, `{ "expected_version": 7 }`; refund amount computed on server | 202 `{ "operation_id": "UUID", "state": "pending", "poll_after_seconds": 3, "cancellation_id": "UUID", "order_state": "cancelled", "refund_state": "pending", "refund_goal_id": "UUID" }`; 409 `CANCELLATION_NOT_ELIGIBLE` / `STALE_VERSION`; missing policy disables action with 409 `POLICY_UNAVAILABLE` |
| Chef UI -> Orders `POST /api/v1/admin/orders/{id}/cancel` | key, `{ "expected_version": 7, "reason": "Chef unavailable" }` | 202 same operation reference; confirmed preview shows remaining payment and prior refunds; 403 capability denial |
| Chef UI -> Payments `POST /api/v1/admin/orders/{id}/refunds` | key, `{ "expected_version": 7, "amount_minor": 2500, "currency": "GBP", "allocations": [{"component_id":"cake-line-1", "amount_minor":2500}], "reason":"Agreed adjustment" }` | 202 `{ "operation_id":"UUID", "state":"pending", "poll_after_seconds":3, "refund_id":"UUID", "refund_state":"reserved", "amount_minor":2500, "currency":"GBP" }`; 422 `INVALID_AMOUNT`/`INVALID_ALLOCATION`; 409 `REFUND_LIMIT`/`RECONCILIATION_REQUIRED` |
| Chef UI -> Orders `POST /api/v1/admin/orders/{id}/start-production` | key, `{ "expected_version": 7 }` | 200 current operation/order reference; 409 `STATE_CONFLICT` |
| UI -> Orders/Payments GET own order / staff refund | existing identity/role; order or refund UUID | 200 safe summary; 401 unauthenticated, 404 absent/foreign, 403 staff capability denial |
| Provider -> Payments webhook | Provider-authenticated event/account/object reference | Verify signature/raw bytes using selected SDK, durable inbox then 2xx; invalid signature 400, unavailable DB 5xx for delivery retry; never acknowledge undurable receipt |

Authorized `GET /api/v1/operations/{id}` returns the current operation/refund summary.
Errors follow K00: `{ "error": { "code":"STALE_VERSION", "message":"Refresh this order", "request_id":"UUID", "retryable":false } }`.

All mutating payloads reject unknown financial fields; 400 malformed/key absent,
409 `KEY_REUSED` for reused key with different canonical payload. Fingerprint
includes method, route/order, amount/currency/allocations/reason/expected version.
Replays reauthorise current actor before exposing original result. Store accepted
command identities without automatic expiry until the retention policy and reuse
semantics are approved; no assumption that a fresh browser key makes cancellation
eligible again. Unique goal + cancelled state prevent a second cancellation under
a different key. Distinct authorised partial commands remain distinct refunds.

Operational proposals follow [architecture](../architecture.md), not competing
packet-specific constants: API deadline 10s; DB transaction lock/statement budget
2s; provider request 5s from durable job; lease 60s with heartbeat/fencing. At most
three database conflict retries with jitter inside the request deadline; async
acceptance target within 3s. Client timeout triggers GET/same-key replay. Job retry
delays 1m/5m/15m/1h then manager attention, always constrained by provider idempotency
retention and uncertainty. Reconciliation uses the proposed five-minute maintenance
cadence; alert oldest urgent unresolved operation after 15m. Exhausted attempts
remain discoverable. Creator recovery targets and sandbox latency/fault evidence
must validate these proposals; no SLA or on-time scheduler guarantee. Production
cutoff safety depends on command-time checks, not that five-minute job cadence.

Create provider key once from opaque operation UUID/account/environment, never
from personal data. Worker leases avoid routine duplicate delivery, but expired
leases do not prove an old network request stopped. Concurrent workers must use
the same immutable provider key/body. Persist first_dispatch_at before sending;
claim completion with lease token/generation; stale responses schedule reconciliation
rather than overwriting newer evidence. Known refund ID means retrieve status,
not another create. Unknown response means keep reservation and look up evidence.

For Stripe **candidate only**, idempotent POST requests replay the saved response,
including 500s; keys may be removed after at least 24 hours, and reuse after pruning
can create a new operation. Therefore no blind refund POST at/after the selected
provider's safe retention boundary. Establish its request deadline margin in the
spike. Past that boundary, lookup/reconcile or require staff investigation; elapsed
time or an empty search alone is not proof of no refund. A new operation/key is
permitted only after definitive nonexecution/failure evidence and fresh balance
validation. [Stripe idempotency](https://docs.stripe.com/api/idempotent_requests), checked 2026-09-21.

Stripe supports multiple partial refunds with a charge-total cap, may hold refunds
pending when its available balance is insufficient, and refunds can later fail.
Some methods require customer action and can move from succeeded back to
requires_action. Local mapping must preserve reservation/attention across those
provider-specific transitions; succeeded is not an irreversible enum shortcut.
Provider-confirmed success is not proof of receipt in the customer's bank.
[Stripe refunds](https://docs.stripe.com/refunds), checked 2026-09-21.

Webhook duplicates/out-of-order payloads are hints for retrieval, not unconditional
state assignments. Coalesce work per capture with a generation/lease, retrieve the
current provider object outside locks and reject stale worker results. Reconcile
again if another event arrived during retrieval; preserve audit of corrections.
Never overwrite success with an older pending event. Verify signatures and account,
environment, charge, amount and currency before applying any provider fact.
[Stripe webhooks](https://docs.stripe.com/webhooks), checked 2026-09-21.
Reconciliation includes complete paginated capture refund records and unresolved
operations, not only delivered webhooks. No provider claim here is integration proof.

or dispatch; API/UI release separately through DELIVERY, release separately authorised.

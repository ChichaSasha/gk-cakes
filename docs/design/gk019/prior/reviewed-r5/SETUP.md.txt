## Configuration and secrets

The following are example names, not an implemented configuration schema. The
selected implementation must supply a committed `.env.example` containing names
and harmless placeholders, plus ignore rules for local secrets.

| Classification | Examples | Location |
| --- | --- | --- |
| Public, deliberately exposed | Site/API origin, shop timezone/currency, provider publishable key where supported | Frontend build/runtime config after review |
| Backend secrets | `DATABASE_URL`, payment secret, webhook signing secret, storage write credential, email API key | Backend secret store; local ignored env for sandbox development |
| Release credentials | Component deploy identity, migration database role | Scoped CI environment/workload identity; separate from application role |
| Creator-only recovery | Provider MFA recovery codes, registrar/account recovery | Personal password manager; not agent context or Trello |

Use separate environments and least-privilege roles. Never ask for raw secrets in
chat, cards or screenshots. The Creator enters secrets directly into the intended
store; the agent verifies the variable/resource exists and behaviour succeeds
without echoing its value. Rotate/revoke exposed credentials and remove exposure
through an authorized incident procedure; deletion from a current file is not
revocation. Do not let frontend `PUBLIC_*`/`VITE_*`/equivalent prefixes expose secrets.

## K00 — common wire and authorization rules

`/api/v1` HTTPS JSON; UUID identifiers; lower_snake_case fields; required fields
listed per command, omitted optional means unchanged/default, explicit null only
for clearing named nullable fields (profile handle, optional note). Unknown mutation
fields rejected. Errors: `{error:{code:"CAPACITY_UNAVAILABLE",message:"Choose another date",request_id:"...",retryable:false}}`.
400 malformed; 401 unauthenticated; 403 role denied; 404 unknown/not-owned resource;
409 STALE_VERSION/state/price/capacity/key conflict; 422 invalid business input;
429 Retry-After; 503 unavailable. No SQL/provider detail or existence oracle.

Bearer token verification uses configured issuer/JWKS/audience/allowed algorithm,
expiry/nbf and subject; never token-supplied key URL. Local active staff membership
is checked on every staff request; manager versus fulfillment duties are explicit.
Object ownership is checked even with a valid token. Guest purchase is owner-confirmed (BO-GK-003.guest_purchase); guests use
high-entropy scoped capability with only digest stored, never public order number.
No identity linking by Instagram handle, typed email or matching delivery address.
CORS allowlists exact UI origins; CSP, output escaping and no private shared cache.
If browser session architecture changes to cookies, CSRF/origin validation and
secure HttpOnly SameSite cookies become mandatory before that change ships.

Mutations carry `Idempotency-Key` (opaque UUID) and existing-object `expected_version`
integer. Scope = authenticated actor/capability + command + resource; unique DB
scope/key and canonical request hash. Same key/same input returns saved operation;
different input yields 409 KEY_REUSED. Money operation identities persist with
financial history, not merely provider key retention. Proposed ordinary-key
retention 30d; expired keys cannot duplicate a business unique relationship.
Any ambiguous commit is looked up before reissuing. Client preserves key across
retry, creates a new key only for a deliberately new operation.

Money: signed 64-bit minor-unit integers, nonnegative bounded inputs and checked
intermediates; currency ISO code and provider-supported exponent, no floats. Dates
`YYYY-MM-DD` are shop-local production days, instants RFC3339 UTC. Slots have stable
IDs, start/end instants and timezone snapshot. Ambiguous DST local entry must select
an explicit offset; nonexistent time rejected. Cutoff compares server time after
locks, not browser clock. User-facing timezone is always labelled.

Read budgets/deadlines and bounded job retry defaults are in architecture.md.
Public lists cursor-paginate <=50 entries; default 20. Reads can retry twice with
jitter inside deadline; mutations retry only using original key. Async operations
return 202 `{operation_id,state:"pending",poll_after_seconds:3}` with authorized
`GET /operations/{id}`. Exhaustion surfaces actionable state, not false failure.

## K03 — price agreement and discount arithmetic

`POST /checkout/quotes` accepts lines `{variant_id,quantity}`, production_date,
pickup_slot_id OR chef_delivery address/window OR customer_arranged handover slot,
discount_code optional. Returns quote ID/version/expiry and immutable proposed
line/recipe/policy snapshots, currency, item subtotal, item discount, delivery fee,
delivery discount, tax, total and availability advisory. Input amount/fee is ignored
or rejected; server validates fulfillment eligibility and stock/capacity.

Proposed policy: one code per order; percent applies to eligible item subtotal only,
free-delivery affects chef delivery only, no stacking; Creator must approve before
implementation. Percent is basis points 0..10000, discount D=floor((eligible_sum*bps+5000)/10000),
allocated to eligible lines by floor proportional shares then largest fractional
remainder, ties stable line ID. Thus item allocations sum exactly to D. Example
1001+1000 at 10%=200, split 100/100, net 1801. Free-delivery cannot reduce goods below
zero. BO-GK-005.vat reports not VAT registered and no separately added VAT; this is not
verified tax exemption/zero-rate advice. Exact rounding/allocation remains blocked;
authoritative tax_amount is shown before payment. Final total is sum of
net lines + net delivery + tax under that approved policy.

Code owns version/eligibility/currency/start/end/usage limit. Hold reserves usage
atomically; success consumes, confirmed-unpaid expiry releases. Pending payment
holds still count. Unique order/code application prevents retry consumption.
Cancellation does not invent eligibility to reuse a limited-use code; Creator
policy decides reinstatement with explicit ledger movement. Orders preserve the
applied rule and allocation, never recompute refunds from today's price/code.

Selected-image wire contract (C12): each ready public catalog image returns

`POST /custom-requests/{id}/summary` requires key plus

belongs to the supplied inspiration and is a published ready image accessible via

Regression: customer displays/selects A, then catalog replaces A with B before
creating the draft or freezing its summary. The explicit A ID yields the exact A
pin/bytes if still permitted, otherwise REFERENCE_UNAVAILABLE and an explicit
reselection path. Never return/pin B without a new customer selection. Generic
no-inspiration request freezes without an image; half-pairs and foreign-image
associations fail without a request image pin.

C12 image preservation: freezing a summary revision atomically records the selected
inspiration_id, image_revision_id, immutable object key/version and safe image
metadata (MIME, dimensions, alt text) beside the exact requested differences. The
Custom module owns the reference pin; Catalog/Storage may replace or archive public
images but cannot mutate pinned bytes or delete an object while any retained request
or quote references it. Pin creation and cleanup admission must serialize on the
same image/object-reference row. A cleanup tombstone prevents new pins; selecting
an already unavailable revision returns409 REFERENCE_UNAVAILABLE and asks the
customer to select a current image, without freezing a false reference. Object
writes use new immutable keys, never overwrite an existing referenced key.
